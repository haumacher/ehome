# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

E-Home: a TopLogic (8.0.0-alpha12, Java 21) web app that imports KNX ETS projects (`.knxproj`) and discovers KNX gateways (Calimero). The app has its own version (`1.0.0-SNAPSHOT`), independent of the TopLogic version.

## Modules

A Maven build of two modules (haumacher/ehome #28); `pom.xml` at the root only aggregates them (it is not their parent):

- `ehome/` — the app (artifact `com.top-logic:de.haumacher.ehome`, parent `tl-parent-app`). Everything of the product, including the rules simulation and its virtual installation (`de.haumacher.ehome.virtual.server`/`.device`: `KnxServer`, `VirtualInstallation`, `GroupStack`, `GroupDevice`; `calimero-server` and its `calimero-device`), the samples (`ehome/samples/`) and the test fixtures. Paths below without a module prefix are relative to `ehome/`.
- `ehome-virtual/` — the development tooling (artifact `de.haumacher.ehome.virtual`, parent `tl-parent-core`, a TopLogic web fragment): the programmable virtual device (memory, properties, programming button, load state machines, `VirtualInterface`, `DeviceStack`), the recorder of ETS downloads and its traces (package `de.haumacher.ehome.virtual.tooling`), the views `WEB-INF/views/virtual/`, `WEB-INF/autoconf/ehome.virtual.config.xml`, its tests (`test.de.haumacher.ehome.virtual.tooling`) and the ETS traces (`ehome-virtual/src/test/fixtures/ets-traces/`). It depends on the app (and on the app's test-jar for the test harness); the app never depends on it, in code or in Maven.
- The app reaches the tooling only through the view layer's overlays: the device tab bar in `projects/devices.view.xml` has the id `device-tabs`, and the tooling's `projects/devices.view.xml` adds the tab "Virtual device" to it with `config:ref="device-tabs"` (TL #29896). New tooling UI hooks in the same way, addressing a keyed element of an app view by its id; a Java hook would be a TopLogic configuration or service-loader extension point in the app.
- Profiles, in the root `pom.xml` and in `ehome/pom.xml`: `development` (active unless another profile of the POM is chosen) builds both modules and puts the tooling on the classpath of the app's `exec:java`; `-Pproduction` builds and starts the app alone. The deployable `ehome/target/ehome.war` never contains the tooling.

## Build, run, verify

- Maven 3.9.16: the wrapper `./mvnw`, or `mvn` from `~/tools/maven` (first on the PATH via `~/.bashrc` and `~/.profile`). TopLogic 8 requires Maven >= 3.8.9; the distribution's `/usr/bin/mvn` is older and must not come first on the PATH.
- Build, from the repository root: `./mvnw install` (both modules); `./mvnw install -Pproduction` (the app alone, as `./mvnw install -pl ehome`). The TopLogic parents come from the Nexus repositories declared in the module POMs.
- Debian package (`doc/debian.md`): `./mvnw install -Pproduction,debian` builds the war with H2 (deploy aspect `ehome/deploy/debian`), `bin/build-deb.sh` packages it for Debian's `tomcat10` (`packaging/debian/`); the workflow `.github/workflows/debian-package.yml` does both on every push to `master` and releases a tag `vX.Y.Z`, and publishes the package in the signed apt repository on GitHub Pages (`bin/apt-repo.sh`, suites `snapshot` and `stable`, https://haumacher.github.io/ehome/). An upgrade of the package stops the app (not Tomcat) and backs up the database first (`packaging/debian/preinst`).
- Agent access (`doc/agent-access.md`): the engine module `tl-layout-view-agent` gives an agent outside the browser the user's session through `/ehome/agent-api` and an access token the user issues (development menu, Agent access); `bin/ehome-agent.py` is the client, the invitation in `~/.config/ehome/agent-invitation` (mode 600).
- Lint: `./mvnw checkstyle:check` from the root checks both modules (rules in the root `checkstyle.xml`: copyright header, tab indentation, imports, braces). It is not bound to the build, so run it after Java edits.
- Run, from the repository root: `./mvnw -pl ehome exec:java` starts the app with Jetty on port 8080 (`-Dtl.port=...` to change), with the tooling (build it first with `./mvnw install` in the root; `-Pproduction` starts without it). The data is in `tmp/` of the working directory, so start from the root (the root `tmp/` holds the data; started in `ehome/`, the app would use `ehome/tmp/`); `-Dh2_name=<dir>/h2;DB_CLOSE_ON_EXIT=FALSE -Dtl_storage_path=<dir>/app-data` starts on other data. `ehome/pom.xml` sets `tl_operation_mode=development` for it (without it, TopLogic 8 runs in production mode). Local runs use H2 (`ehome/deploy/local`); its `metaConf.txt` reads `devel-secrets.xml`, which supplies the password of the local H2 (TL #29948: database passwords are named secrets without default; the Debian package writes `h2_passwd` into `/etc/ehome/ehome.env`). The knowledge base runs without branch support (`top-logic.singleBranch.config.xml` in `WEB-INF/conf/metaConf.txt`; see `doc/tl-todo.md`, TL #29876): a database created with branches does not fit and needs a fresh `tmp/`. The launch config `bin/launch/Start E-Home.launch` sets `-Dtl_initial_password=root1234` for the initial `root` login. The context path is `ehome` (`tl.contextPath` in `ehome/pom.xml`, also the name of the deployable war `ehome/target/ehome.war`); the UI is at `/ehome/view/` (the classic `/servlet/LayoutServlet` only shows the engine's administration); log in through the in-app dialog (there is no `login.jsp` any more).
- Model access rights are deny-by-default in TopLogic 8. `WEB-INF/autoconf/ehome.security.config.xml` defines two global roles, held through group membership: `ehome.Installer` (group `ehome.installers`: reads and edits everything, imports, programs devices, deploys) and `ehome.Viewer` (group `ehome.viewers`: reads only); administrators (`root`) bypass the checks. Projects, controllers and the master-data singletons decide by grants on their modules; every other type is a composition part and delegates to its container. The controller token has a read grant without roles (nobody but an administrator reads it through the model). A new type that no composition holds needs a role parent rule and grants there, or `TestSecurityCoverage` (switched on in `ehome-testSettings.config.xml`) fails. Java code (import, programming, deployment, the TL-Script functions of `ehomeConf.config.xml`) is not access checked: a view command that changes data through it carries an `<access>` check (`<operation name="Write" object="$…"/>`, TL #29856); a read-only one carries a `Read` check, a network search without an object a check on the security root, which both E-Home roles may read (haumacher/ehome #65). `TestCommandAccessProbe` (in each module, over the shared `test.de.haumacher.ehome.view.ViewCommandScan`) fails on a command without an `<access>` check that runs a transaction, an action of the app, or an `<execute-script>` calling a TL-Script function of the app with side effects (`GenericMethod#isSideEffectFree()` false: a writing function must say so, a reading one should declare itself side-effect-free), and on a check that does not build.
- Tests: `./mvnw test -DskipTests=false` in the root runs the suite of each module (the TopLogic parent skips tests by default); `-Pproduction` (or `-pl ehome`) the app's alone. In each module the generic `test.TestAll` from tl-basic collects every test under the module's `src/test/java` and adds TopLogic conformance checks (copyright comments, normalized layouts, JSPs, I18N). Surefire runs in the module directory: the tooling's tests read the samples as `../ehome/samples/`, the app's round trip `../doc/knx/not-modeled.txt`. Test classes go in package `test.<package>` and provide `suite()`; for KB/model access, wrap them like `TestEtsImport` (`KBSetup.getSingleKBTest(ServiceTestSetup.createSetup(..., ModelService.Module.INSTANCE))`). Test-only config lives in `src/test/webapp/WEB-INF/conf/`.
- All test classes of a module share one knowledge base in one JVM, in the order of their packages; the tooling's suite has a database of its own and imports its samples there again. The shared data (master data, manufacturers with catalogs and programs) stays: an import into an empty database costs seconds per program, a further import of the same sample about one. A test deletes only its projects and asserts project-relative state or shared objects by their IDs, never the counts of a fresh database (`test.de.haumacher.ehome.importer.SharedData`); a test that needs a specific state of the mask versions establishes it with `SharedData.resetMaskVersions`. Only `test.de.haumacher.ehome.roundtrip.TestRoundTrip` (the `.knxproj` export, `doc/knx/export.md`) empties the E-Home data of the database (once, before its samples); it runs first in the database because its setup starts only the model service (the framework runs tests with fewer services first), so the deletion is free — a new test class gets the usual services (model, label provider, person manager), or it would run before the round trip and its data would be deleted again. Tests must not rely on data imported by earlier tests: they import what they need and delete their projects again. What the round trip may lose is listed in `doc/knx/not-modeled.txt`; its exports and differences land in `ehome/target/roundtrip/`.
- Derived attributes (`<storage-algorithm><query>`) are computed with the reading user's access rights; without a person and outside the system context they read as `null`. Since alpha12 a test runs in the system context, where the access checks are bypassed (TL #29798); `TestEtsImport.derived` reads them as `root`. A test of access rights runs its checks with security on and the person in a person context (`TestAccessRights#runTest`, `TLContextManager.inPersonContext`).
- Verify behavior changes by running the tests, then starting the app and checking it in the browser. For ETS import, use the sample projects in `ehome/samples/` (`Test.knxproj` has a single device); for the controller with the test system on the desk, the test home (`doc/test-home.md`).
- Commit to `master` and push to `origin/master` after every verified change (standing directive). Feature branches and pull requests are for external contributors. The working method (agent briefs, probe review, gate, run loop) is the skill `ehome-workflow` in `.claude/skills/`.

## Generated code

- The Java model bindings in `ehome/src/main/java/de/haumacher/ehome/model/{core,operational}/` are generated from `ehome/src/main/webapp/WEB-INF/model/ehome.{core,operational}.model.xml` by `tl:generate-java` (configured in `ehome/pom.xml`). The tooling has no model of its own. Every run regenerates `internal/*Base.java`, `internal/*Impl.java`, the `*Factory.java` files, the classes of the enumerations (`<Enum>.java`, its name and classifier constants) and the deprecated `*Constants.java` stubs: never edit them. Only the interface `X.java` is created once and is meant for hand-written code; own methods go into it as default methods.
- After a model change, run `cd ehome && ../mvnw tl:generate-java`, then build. The generator reads the model from the module's sources (`src/main/webapp`) and resolves the engine's web fragments through Maven (TL #29789), so no install is needed before it. It is not bound to the build: a run costs about 25 s and rewrites every generated file.
- A model change the automatic model upgrade at startup would apply destructively to an existing database (it deletes and creates instead of moving: a class moved to another module, a renamed attribute) gets a data migration in `ehome/src/main/webapp/WEB-INF/kbase/migration/ehome/` (migration module `ehome`, `WEB-INF/autoconf/ehome.migration.config.xml`); the first one is `Ticket_29806_Dissolve_ehome_mask`. Check on a copy of `tmp/` (`-Dehome.dataDir=<copy>`) that the log shows the migration and no "Started incremental model upgrade" for its part. `TestConsistentMigrationScripts` (in `test.TestAll`) checks the scripts.
- The header of the generated files is `copyrightHeader` of the goal in `ehome/pom.xml` (`Copyright (c) 2018 Bernhard Haumacher`, a fixed year: with `${year}` every run in a new year would rewrite the header of every generated file).
- Views (`WEB-INF/views/**`), `WEB-INF/autoconf/*.config.xml`, model XML, and `.properties` resources can be edited directly as text.

## UI (TL views)

- The UI lives in `ehome/src/main/webapp/WEB-INF/views/*.view.xml` (module `tl-layout-view`), the tooling's in `ehome-virtual/src/main/webapp/WEB-INF/views/`; the app has no classic layouts (`WEB-INF/layouts/`) any more. Read the `view-layer` chapter of the developer docs (tl-mcp `list_docs`/`read_doc`) before editing views; `tl-demo-react` in the engine sources is the reference application.
- `app.view.xml` is an overlay of the engine's shell (sidebar items). Structure trees create nodes through `create-node.view.xml` and the `new` command clique (configured in `WEB-INF/conf/ehomeConf.config.xml`, as is the TL-Script function `knxNetworkInterfaces()`).
- App-specific view actions are Java classes with a `@TagName` config (`import-ets-project`, `discover-knx-gateways`).
- A changed `.view.xml` is not picked up by a running app; restart it. `TestViewsLoad` (in each module) loads and instantiates every view, so a configuration error of a view fails the suite.
- `doc/knx/schema-coverage.md` tracks which parts of the KNX project schema the model covers; extend the model there in its own terms, not as a copy of the XML.
- `doc/tl-todo.md` lists the gaps that wait for a newer TopLogic version (tree tables, Excel export, TL #29791). Engine gaps and defects get a TL ticket, a minimal workaround (or none, leaving the problem visible) and an entry there. A TopLogic upgrade happens only when the user asks for one; then check every entry and undo the workarounds whose fix has shipped. Do not look for newer engine versions or poll the tickets on your own.

## Stale files (ignore)

- `bin/build.xml` (old Ant build), `bin/launch/Generate ehome.operational.launch` (old layout, references a nonexistent `ehome.model.xml`), `ehome/.factorypath` (wrong user and version), and `target/` in the root (the build output before the split into modules).

## Code style

- Java sources and `.properties` resource bundles are UTF-8 (TopLogic 8); write umlauts directly, not as `\uXXXX` escapes.
- Indent with tabs. Every Java file starts with:
  ```
  /*
   * Copyright (c) <year the file was created> Bernhard Haumacher
   */
  ```
- Put UI texts in `I18NConstants` classes as `ResKey` fields, with the English text in an `@en` javadoc tag (TopLogic convention).
