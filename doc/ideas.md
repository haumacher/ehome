# Ideas

Open points of E-Home and of its controller HomeControl (`haumacher/homecontrol`): proposals that
were discussed but not decided, or deliberately put off. This file is the master list for both
repositories. An entry is no ticket: an implementing agent does not work on it. When the user
agrees on its design, it becomes a ticket (one per repository side) and leaves this list.

Each entry: what it is about, the user's words, what exists today (with references), the open
questions, and why it waits.

## Zigbee: a datapoint per function without the extra step

The user: "dort muss man explizit für jede Funktion einen Datenpunkt anlegen oder auswählen. Wenn
das ohnehin nur genau einer pro Gerät sein kann, dann ergibt das einfach keinen Sinn."

Today:
- A Zigbee function has at most one datapoint (`ZigbeeFunction#datapoints`,
  `ehome/src/main/webapp/WEB-INF/model/ehome.zigbee.model.xml:309`; the image refuses a function
  bound twice, homecontrol `spec/zigbee.md:55`).
- The tab "Zigbee" creates the datapoints per device ("Create datapoints", with name, type and
  reporting from the Zigbee catalog) or per function ("Create datapoint", "Bind datapoint",
  "Unbind") (`ehome/src/main/webapp/WEB-INF/views/projects/zigbee.view.xml:229`, `:433`, `:462`,
  `:490`).
- The controller gives a device without any binding generic datapoints
  `zigbee.<ieee>.<endpoint>.<function>` (homecontrol `spec/zigbee.md:19`, `:26`).
- What the datapoint of its own is good for: a stable name for rules, schedules and control pages;
  replacing a broken device by binding its datapoints to the new one; a function the export no
  longer lists stays marked `absent` while a datapoint is bound to it (`ZigbeeImport.java:41`).

Discussed: create the datapoints with the import, show and edit them in the function table, turn
"Bind" into "Replace device". Against it, the user: creating them directly gives the datapoints
unreadable technical names. "Wir lassen das erst mal so wie es ist."

Open: how the installer gets readable names without a step per function.

## Zigbee: switches bound directly to actuators

The user: "Man kann aber Zigbee Geräte im Zigbee Netzwerk direkt miteinander verbinden, indem man
dort dieselben Datenpunkte verwendet - z.B. Schalter und Steckdose?"

Today:
- In Zigbee itself a switch's client cluster On/Off can be bound to a socket's server cluster (ZDO
  Bind) or to a Zigbee group the socket is a member of (close to a KNX group address); the switch
  then commands the socket without the coordinator, also while the controller is down.
- The firmware binds every mapped cluster to the coordinator only (homecontrol
  `doc/zigbee.md:194`); groups and scenes are listed under "Not done" (`doc/zigbee.md:389`).
- In E-Home a datapoint's `zigbee` member names one function of one device (homecontrol
  `spec/zigbee.md:30`), and a datapoint is either `knx` or `zigbee` (a datapoint has one owning
  technology, homecontrol `core/include/hc/technology.h:11`). Switch and socket get two datapoints;
  a rule on the controller couples them, as it couples Zigbee and KNX.

Open (proposals, not decided):
1. Zigbee groups or single bindings (proposed: groups; one entry in the switch's binding table for
   several sockets, and the concept of a KNX group address).
2. Whether the controller still sees the commands (proposed: keep the switch's binding to the
   coordinator, so its datapoint, rules and history stay).
3. Which clusters (proposed: buttons only, client clusters On/Off 6 and Level Control 8, the
   `action` function).
4. A factory-reset device loses its bindings; the firmware already detects it and interviews again
   (homecontrol `doc/zigbee.md:199`), the binding again must hook in there. Further: the
   simulation in E-Home, the binding table limits of the devices, an older firmware under I4/I5 of
   homecontrol `spec/runtime-image.md`.

Would be two tickets: homecontrol (bindings/groups, image format) and ehome (model, editor, image
writer, simulation).

## KNX Secure

The user asked: "KNX secure - what is it and how does it work?" The answer was put off ("put it
in ideas.md for now") until the scope is chosen.

What it is (two independent mechanisms):
- *KNX Data Secure*, end to end on the telegram: a Secure APDU with AES-128-CCM (always a 4-byte
  MAC, optionally encrypted), replay protection by a 48-bit sequence number per sender that each
  receiver checks against its Security Individual Address Table (sync request/response to
  realign). Keys: the FDSK (printed on the device, QR code with the serial number) only for the
  first commissioning, which writes a tool key per device generated by the tool (the FDSK is then
  dead; a lost tool key needs a master reset); a group key per secured group address, held by
  every device linked to it. Non-secure devices cannot take part in a secured group address. The
  download writes the security tables (group keys, senders, own sequence number).
- *KNX IP Secure*, on the KNXnet/IP connection: unicast (tunnelling, device management) in a
  session set up by X25519, authenticated by the interface's device authentication code and a
  per-tunnel user password (PBKDF2-HMAC-SHA256), every frame in a `SECURE_WRAPPER` (AES-128-CCM,
  16-byte MAC); routing multicast with a shared backbone key and timer-based freshness. A router
  with IP Secure refuses plain tunnelling.
- ETS keeps the keys in the project, encrypted with a key derived from the project password,
  and exports them as a keyring (`.knxkeys`) — not yet checked against a secured project.

Today:
- Not supported: `doc/programming.md:247` ("KNX Secure devices are not supported"), `:262`; the
  import does not read `IsSecureEnabled`, `SecurityRequired`, `MaxSecurity*` or the project's
  keys (`doc/knx/schema-coverage.md:109`); the virtual installation and the virtual interface
  have none (`ehome/src/main/java/de/haumacher/ehome/virtual/server/KnxServer.java:35`,
  `ehome-virtual/.../tooling/server/VirtualInterface.java:25`).
- HomeControl tunnels plain KNXnet/IP (`core/include/hc/knx/tunnel.h`); no spec mentions security.
- Building blocks: Calimero 2.6 (already a dependency) has `tuwien.auto.calimero.secure`
  (`SecureApplicationLayer`, `Keyring`, `SecurityControl`) and `mgmt.SecureManagement`; the
  firmware has mbedTLS (`core/include/hc/platform/crypto.h:13`: AES-CCM, X25519, PBKDF2).
- No secure-capable product in the samples (no `IsSecure*` in the catalogs of
  `ehome/samples/KNX-Testsystem*.knxproj`), so nothing to test on.

What it would take, by part:
- (a) Import of secured projects without losing the keys (needs the project password).
- (b) Commissioning from E-Home: FDSK input (typed or QR) on the device, generation and storage of
  tool and group keys, secure management in the download plan, the security tables. Keys are
  secrets: under deny-by-default the pattern of the controller token (read grant without roles).
- (c) The controller on secured group addresses: group keys in its image, its address in the
  receivers' sender tables, a sequence counter that survives reboots and flashes and is never
  reused (written ahead in NVS in blocks).
- (d) The controller's tunnel to a router with IP Secure: X25519 session, the tunnel's user
  password and the router's authentication code as settings.
- The simulation (virtual device and installation) with Data Secure.

Open questions, with the proposals made:
1. Which part first? Proposed: (d), the smallest (firmware plus a password input) and the first
   thing an installer meets with a secure router; (b) and (c) together, since the controller's
   keys come from E-Home's key management.
2. Hardware: proposed one Data Secure actuator and an IP Secure router or interface for the test
   system; until then Calimero's `SecureApplicationLayer` in the virtual device.
3. Secrets in the image: proposed an encrypted section of their own, not the signed-only part
   (`ehome/src/main/java/de/haumacher/ehome/connection/Signatures.java`), with a key per
   controller established at enrollment (`connection/Enrollment.java`).

Why it waits: the scope (question 1) is not chosen.
