# Ideas

Open points of E-Home and of its controller HomeControl (`haumacher/homecontrol`): proposals that
were discussed but not decided, or deliberately put off. This file is the master list for both
repositories. An entry is no ticket: an implementing agent does not work on it. When the user
agrees on its design, it becomes a ticket (one per repository side) and leaves this list.

Each entry: what it is about, the user's words, what exists today (with references), the open
questions, and why it waits.

## Zigbee: a datapoint per function without the extra step

The user: "dort muss man explizit für jede Funktion einen Datenpunkt anlegen oder auswählen. Wenn
das ohnehin nur genau einer pro Gerät sein kann, dann ergibt das einfach keinen Sinn."

Today:
- A Zigbee function has at most one datapoint (`ZigbeeFunction#datapoints`,
  `ehome/src/main/webapp/WEB-INF/model/ehome.zigbee.model.xml:309`; the image refuses a function
  bound twice, homecontrol `spec/zigbee.md:55`).
- The tab "Zigbee" creates the datapoints per device ("Create datapoints", with name, type and
  reporting from the Zigbee catalog) or per function ("Create datapoint", "Bind datapoint",
  "Unbind") (`ehome/src/main/webapp/WEB-INF/views/projects/zigbee.view.xml:229`, `:433`, `:462`,
  `:490`).
- The controller gives a device without any binding generic datapoints
  `zigbee.<ieee>.<endpoint>.<function>` (homecontrol `spec/zigbee.md:19`, `:26`).
- What the datapoint of its own is good for: a stable name for rules, schedules and control pages;
  replacing a broken device by binding its datapoints to the new one; a function the export no
  longer lists stays marked `absent` while a datapoint is bound to it (`ZigbeeImport.java:41`).

Discussed: create the datapoints with the import, show and edit them in the function table, turn
"Bind" into "Replace device". Against it, the user: creating them directly gives the datapoints
unreadable technical names. "Wir lassen das erst mal so wie es ist."

Open: how the installer gets readable names without a step per function.

## Zigbee: switches bound directly to actuators

The user: "Man kann aber Zigbee Geräte im Zigbee Netzwerk direkt miteinander verbinden, indem man
dort dieselben Datenpunkte verwendet - z.B. Schalter und Steckdose?"

Today:
- In Zigbee itself a switch's client cluster On/Off can be bound to a socket's server cluster (ZDO
  Bind) or to a Zigbee group the socket is a member of (close to a KNX group address); the switch
  then commands the socket without the coordinator, also while the controller is down.
- The firmware binds every mapped cluster to the coordinator only (homecontrol
  `doc/zigbee.md:194`); groups and scenes are listed under "Not done" (`doc/zigbee.md:389`).
- In E-Home a datapoint's `zigbee` member names one function of one device (homecontrol
  `spec/zigbee.md:30`), and a datapoint is either `knx` or `zigbee` (a datapoint has one owning
  technology, homecontrol `core/include/hc/technology.h:11`). Switch and socket get two datapoints;
  a rule on the controller couples them, as it couples Zigbee and KNX.

Open (proposals, not decided):
1. Zigbee groups or single bindings (proposed: groups; one entry in the switch's binding table for
   several sockets, and the concept of a KNX group address).
2. Whether the controller still sees the commands (proposed: keep the switch's binding to the
   coordinator, so its datapoint, rules and history stay).
3. Which clusters (proposed: buttons only, client clusters On/Off 6 and Level Control 8, the
   `action` function).
4. A factory-reset device loses its bindings; the firmware already detects it and interviews again
   (homecontrol `doc/zigbee.md:199`), the binding again must hook in there. Further: the
   simulation in E-Home, the binding table limits of the devices, an older firmware under I4/I5 of
   homecontrol `spec/runtime-image.md`.

Would be two tickets: homecontrol (bindings/groups, image format) and ehome (model, editor, image
writer, simulation).

## KNX Secure

The user asked: "KNX secure - what is it and how does it work?" The answer was put off ("put it
in ideas.md for now") until the scope is chosen.

What it is (two independent mechanisms):
- *KNX Data Secure*, end to end on the telegram: a Secure APDU with AES-128-CCM (always a 4-byte
  MAC, optionally encrypted), replay protection by a 48-bit sequence number per sender that each
  receiver checks against its Security Individual Address Table (sync request/response to
  realign). Keys: the FDSK (printed on the device, QR code with the serial number) only for the
  first commissioning, which writes a tool key per device generated by the tool (the FDSK is then
  dead; a lost tool key needs a master reset); a group key per secured group address, held by
  every device linked to it. Non-secure devices cannot take part in a secured group address. The
  download writes the security tables (group keys, senders, own sequence number).
- *KNX IP Secure*, on the KNXnet/IP connection: unicast (tunnelling, device management) in a
  session set up by X25519, authenticated by the interface's device authentication code and a
  per-tunnel user password (PBKDF2-HMAC-SHA256), every frame in a `SECURE_WRAPPER` (AES-128-CCM,
  16-byte MAC); routing multicast with a shared backbone key and timer-based freshness. A router
  with IP Secure refuses plain tunnelling.
- ETS keeps the keys in the project, encrypted with a key derived from the project password,
  and exports them as a keyring (`.knxkeys`) — not yet checked against a secured project.

Today:
- Not supported: `doc/programming.md:247` ("KNX Secure devices are not supported"), `:262`; the
  import does not read `IsSecureEnabled`, `SecurityRequired`, `MaxSecurity*` or the project's
  keys (`doc/knx/schema-coverage.md:109`); the virtual installation and the virtual interface
  have none (`ehome/src/main/java/de/haumacher/ehome/virtual/server/KnxServer.java:35`,
  `ehome-virtual/.../tooling/server/VirtualInterface.java:25`).
- HomeControl tunnels plain KNXnet/IP (`core/include/hc/knx/tunnel.h`); no spec mentions security.
- Building blocks: Calimero 2.6 (already a dependency) has `tuwien.auto.calimero.secure`
  (`SecureApplicationLayer`, `Keyring`, `SecurityControl`) and `mgmt.SecureManagement`; the
  firmware has mbedTLS (`core/include/hc/platform/crypto.h:13`: AES-CCM, X25519, PBKDF2).
- No secure-capable product in the samples (no `IsSecure*` in the catalogs of
  `ehome/samples/KNX-Testsystem*.knxproj`), so nothing to test on.

What it would take, by part:
- (a) Import of secured projects without losing the keys (needs the project password).
- (b) Commissioning from E-Home: FDSK input (typed or QR) on the device, generation and storage of
  tool and group keys, secure management in the download plan, the security tables. Keys are
  secrets: under deny-by-default the pattern of the controller token (read grant without roles).
- (c) The controller on secured group addresses: group keys in its image, its address in the
  receivers' sender tables, a sequence counter that survives reboots and flashes and is never
  reused (written ahead in NVS in blocks).
- (d) The controller's tunnel to a router with IP Secure: X25519 session, the tunnel's user
  password and the router's authentication code as settings.
- The simulation (virtual device and installation) with Data Secure.

Open questions, with the proposals made:
1. Which part first? Proposed: (d), the smallest (firmware plus a password input) and the first
   thing an installer meets with a secure router; (b) and (c) together, since the controller's
   keys come from E-Home's key management.
2. Hardware: proposed one Data Secure actuator and an IP Secure router or interface for the test
   system; until then Calimero's `SecureApplicationLayer` in the virtual device.
3. Secrets in the image: proposed an encrypted section of their own, not the signed-only part
   (`ehome/src/main/java/de/haumacher/ehome/connection/Signatures.java`), with a key per
   controller established at enrollment (`connection/Enrollment.java`).

Why it waits: the scope (question 1) is not chosen.

## Time programs: further loops, calendars, commanding the state

The first cut is filed (haumacher/ehome #140, haumacher/homecontrol#84): a rule with states plus a
timeline of day plans with clock and sun moments, assigned by default and by weekday. Put off in
the round of 2026-11-12, to be described by the spec's assignment model but not implemented yet.

The user: "there might be other kinds of schedule loops - day, month, year? Are there other
possible time series? A calendar with holidays would be such a non-cyclic schedule. We can now
think through the 'whole thing' - even if we only implement a part of it."

Today:
- Exceptions and vacation ranges are "not yet specified" for the schedule entries (homecontrol
  `spec/schedules.md:258`); the kind `dates` lists up to 128 dates (`spec/schedules.md:144`).
- The house mode block has a `vacation` input, a switch (homecontrol `spec/blocks.md:1610`).
- A rule's state changes only by a transition of the rule; there is no "set state" from outside
  (homecontrol `spec/rules.md:254`).

Open (proposals, not decided):
1. Further assignments of a day plan, the most specific winning: day of the month; a date or a
   range of the year (24 December; the season 1 October to 30 April); a single date.
2. Calendars: a named set of dates and ranges of its own that several programs use ("Holidays",
   "Vacation", "Bin collection"). Who maintains it: proposed the inhabitant on the device, with
   initial content from the image, and public holidays computed by E-Home per region and shipped
   for some years ahead; or the device computes them.
3. A plan chosen by a condition datapoint (a vacation switch): a selector like a calendar, but no
   time series.
4. Commanding the state datapoint `rule/<ruleId>/state` ("state X until the next switching point"
   from a control page). Until then a page writes a virtual datapoint and the rule has a reaction
   per state. Proposed: see first whether that is too clumsy in practice.
5. The form of a timeline in the rule text language (`RuleText`).

Why it waits: the first cut comes first.

## Controls derived from the connections: an operator's manual

The reverse direction of "configure by intent" (haumacher/ehome #131, #146, #147), put off in the
round of 2026-11-12: #131 builds an installation from the ground up; this describes one that
exists.

The user: "the reverse - deriving controls from connections would create a useful description of
an installation - an operator's manual."

Today:
- The function proposal links a key to the function of the actuator channel whose first address
  the key sends on (`ehome/src/main/java/de/haumacher/ehome/runtime/FunctionProposal.java`, class
  comment "Candidates, linked by group addresses"; `:644`: "the key operates the actuator's
  channel"). The link decides which functions are proposed and is not kept.
- A control (source, function, operation) becomes an object with #147.

Open (proposals, not decided):
1. The proposal keeps the links it finds as controls, so an imported installation shows up in the
   same view as one built by intent.
2. The operation of such a control: which preset (#146) a configured channel matches, by comparing
   its parameter settings with the presets of its template; without a matching preset the control
   has a source and a function but no operation.
3. The manual itself: a document per room ("Taste 1 by the door toggles the ceiling light") from
   the controls, for the inhabitant.

Why it waits: it needs the controls and presets of #146 and #147 first.

## Shared service: self-registration and inviting people without an account

Put off in the round of 2026-11-12, when the access per project was filed (haumacher/ehome #152):
accounts are created by administrators, and a project owner adds only existing accounts.

The user: "Administrators create "initial" users - when self-registration becomes available, we'll
add it."

Today:
- The engine's self-service invites a person by mail to create an account (TL #30041, in
  8.0.0-alpha12.820, modules `tl-security-selfservice-core` and `tl-layout-view-selfservice`); the
  invitation is an administrator's, and it does not add to an existing account. E-Home does not
  depend on these modules (`ehome/pom.xml`).
- Not in a release up to 8.0.0-alpha12.820: the language of an invitation and editable mail texts
  (TL #30223), open self-registration with approval, account lock and captcha (TL #30183).
- Mail must be configured for either.

Open (proposals, not decided):
1. Open registration on the hosted service once TL #30183 has shipped: directly or with an
   administrator's approval; whether a registered account may create projects at once.
2. A project owner invites an address without an account: E-Home sends the engine's invitation and
   the new account joins the project when it is accepted. Not verified: whether a non-administrator
   can create an engine invitation and whether it can carry "join this project"; if not, a TL
   ticket.
3. Whether an account that was only invited to a project may create projects of its own (proposed:
   not until an administrator grants it).

Why it waits: an engine upgrade the user asks for, and the access per project first.

## Scan: candidate products by the hardware type

Came up with haumacher/ehome#206 (the hardware type shown as "Bestellnummer"); not discussed further.

Today:
- The scan reads the hardware type (device object, property 78,
  `ehome/src/main/java/de/haumacher/ehome/scan/BusScanner.java:462`); the device stub shows it as
  "Hardware-Typ" (`ehome/src/main/webapp/WEB-INF/views/projects/devices.view.xml:926`).
- An application program checks it when loading (`LdCtrlCompareProp PropId="78"`, e.g.
  `InlineData="00000000030D00000000"` in the MDT program `M-0083_A-000C-21-83B5` of
  `ehome/samples/KNX-Testsystem.knxproj`);
  the catalog match uses it only to exclude programs whose application number and version already
  match (`scan/CatalogMatch.java:175-178`).

Idea: for a device the catalog does not identify by application number and version, list the
manufacturer's programs whose load procedure compares property 78 with the hardware type read, as
candidates for "Zuordnen".

Open: whether manufacturers assign hardware types uniquely enough for this; how the candidates are
offered (a choice in "Zuordnen", or only a hint which product data to import).

## Rules: reaction types and a conditional action

The user: "Zustände und Bedingungen sind optional - aber in der starren Struktur muss man sie immer
mitlesen und das macht das noch unübersichtlicher. Eigentlich sind das unterschiedliche
Reaktionstypen (zustandsbehaftet oder nicht) und verschiedene Aktionstypen (bedingt und nicht
bedingt)." Put off: "wir machen das erst mal minimal" (the labels: haumacher/ehome#214).

Today:
- A reaction has triggers, an optional condition, actions, else-actions, and in a rule with states
  `from` and `to` (homecontrol `spec/rules.md:255-262`); the form shows condition, from, to, then
  the triggers, then Dann/Sonst (`ehome/src/main/webapp/WEB-INF/views/projects/rules.view.xml:383-820`);
  a transition's exit and entry actions are edited at the states and not visible at the reaction.
- The firmware has no conditional action (`spec/rules.md:300-312`).

Proposed:
- Two reaction types chosen at creation: *Reaktion* ((in state) · when · actions) and
  *Zustandswechsel* (from · when · (guard) · actions · to, with the exit/entry actions shown
  read-only); the form shows only what the type has.
- A conditional action "Falls … dann … sonst …" with its own action lists; a firmware action `if`
  (`condition`, `then`, `else`, a nesting limit), the reaction's `condition`/`elseActions` kept for
  older images, an older firmware refusing an image with `if` (I4/I5); existing rules migrated
  (condition + actions + else without `to` → one conditional action; with `to` → a transition with
  the condition as its guard).

Open: nesting of conditional actions (proposed: up to depth 4); keeping the guard of a transition
(proposed: yes, it decides whether the state changes).

## Chart editor: finding datapoints by unit and room, the right axis preset

Asked how to configure a chart with several values ("alle Temperaturkurven" or "die Temperatur und
den Ventilstand (2 Achsen)"), the user, after being shown that it exists: "lassen wir erst mal so wie
es ist."

Today:
- A chart's series are added several at a time in the dialog `projects/page-choose.view.xml` (table
  with multi-selection, `:48`; columns name, type, id in the image, value type, history, `:54-104`);
  each series has its axis, label and consolidation (`ChartSeries`,
  `ehome/src/main/webapp/WEB-INF/model/ehome.runtime.model.xml:4104`), the chart its bounds per axis
  and reference lines.

Proposed, not decided:
- (a) Columns DPT/unit and room in the dialog, to sort and filter e.g. all "9.001 / °C".
- (b) The axis preset when adding: with two different units in a chart, the series of the second
  unit go to the right axis; a third unit gets no preset.
