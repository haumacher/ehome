# KNX project schema: what the model covers

Comparison of the KNX project schema version 11 (`http://knx.org/xml/project/11`, ETS 4; the version of the fixtures in `samples/`) with the E-Home model and the ETS import (`etsImporter.xml`). The element-by-element table is in [schema-11-coverage.md](schema-11-coverage.md), generated by [schema-coverage.py](schema-coverage.py):

```
python3 doc/knx/schema-coverage.py KNXSchema.xsd src/main/java/de/haumacher/ehome/importer/etsImporter.xml
```

The XSD itself is not public and not in the repository.

## Overall

- Of 408 element paths of the schema, 251 are handled by the import; of 1138 attribute slots, 705 are read. The content of the `Languages` sections is read by a handler of its own (`translations`) and shows as not handled in the table.
- The model has a counterpart for exactly what the import reads, and almost nothing more. So "covered by the model" and "read by the import" mean the same thing here.
- IDs: the import keeps the `Id` ETS wrote (`extId`). An object created in the app gets an ID of the same shape (`de.haumacher.ehome.knx.ExtIds`): the ID of the object it belongs to and a number from a sequence of that scope, above every number imported there; types, enumeration entries, communication objects and products are named by their name, value, object number and order number, as in ETS. Switches, cases and the channel independent part have no ID (`choose`, `when` and `ChannelIndependentBlock` have none in ETS).
- Files: a project file (`.knxproj`, imported in the projects view) and the product file of a manufacturer (`.knxprod`, imported in the catalog view, `ImportProductDataAction`) are read with the same mapping; a product file is a project file without the project part (`knx_master.xml` and the `M-xxxx/` folders). The import of a product file refuses a file holding a project (`P-xxxx`), baggage (`Baggages`, ETS 5/6: pictures, help and plug-in files) or an encrypted entry, and a file without manufacturer data. What a project or product file holds that the catalog already has is reused by its ID; a known application program is skipped.
- Many unread attributes are irrelevant for E-Home (ETS bookkeeping: `Hash`, `NonRegRelevantDataVersion`, `CompletionStatus`, `LastModified`, passwords, history, to-dos). The gaps below are those that matter for understanding or operating an installation.

Download data, deliberately not read (gap 9). `DynamicTableManagement`, the offsets of union members and the overrides of a `ComObjectRef` were added for the download image (haumacher/ehome #6): ETS places the association table right after the address table, writes union members at their offset and takes the flags of the reference in effect.

- `Static/Extension` (with `Baggage`), `Static/BinaryData`, `Baggages`: plug-ins and files of ETS (download plug-ins, data handlers, help); E-Home cannot run ETS plug-ins. A program that requires one (`Extension@EtsDownloadPlugin`, `RequiresExternalSoftware`) cannot be downloaded without it either; #7 has to refuse such programs, which needs `Extension` read then.
- `Static/FixupList`: addresses of mask entry points (`MaskEntry`) patched into the code of a segment, for programs calling system functions of BCU 1/2 masks. No sample has one; #6 needs it for such programs (the mask entries are imported already).
- `Static/DeviceCompare` (`ExcludeMemory`, `ExcludeProperty`): what ETS ignores when comparing a device with the project; needed only for a compare function after #7.
- `ModuleDefs` and module instances (dynamic modules of newer schemas): not in schema 11.
- `MaskVersion/HawkConfigurationData/InterfaceObjects` (the property data types of the interface objects of a mask) and `HawkConfigurationData@Ets3SystemPlugin`: describe properties for the ETS property editor; a download writes properties by the data the load procedure names.
- `MediumTypes` (`Id`, `Number`, `Name`, `Text`, `DomainAddressLength`): the medium is an enumeration of its own (`ehome.common:Medium`, read from `MediumTypeRefId`).
- `Options`: read are `PreferPartialDownloadIfApplicationLoaded`, `SetObjectTableLengthAlwaysToOne`, `TextParameterEncoding`, `TextParameterEncodingSelector`, `TextParameterZeroTerminate`, `ParameterByteOrder`, `LegacyNoPartialDownload`, `LegacyNoMemoryVerifyMode`, `LegacyKeepObjectTableGaps`, `DeviceInfoIgnoreRunState`, `DeviceInfoIgnoreLoadedState`. Not read: `EasyCtrlModeModeStyleEmptyGroupComTables` (Easy controller mode), `PartialDownloadOnlyVisibleParameters` (an ETS optimization of partial downloads), `LegacyNoOptimisticWrite`, `LegacyDoNotReportPropertyWriteErrors`, `LegacyNoBackgroundDownload`, `LegacyDoNotCheckManufacturerId`, `LegacyAlwaysReloadAppIfCoVisibilityChanged`, `LegacyNeverReloadAppIfCoVisibilityChanged`, `LegacyDoNotSupportUndoDelete`, `LegacyAllowPartialDownloadIfAp2Mismatch`, `LegacyProxyCommunicationObjects` (behavior of the ETS user interface and of its background download), `DeviceCompareAllowCompatibleManufacturerId`, `Comparable`, `Reconstructable` (device compare), `LineCoupler0912NewProgrammingStyle` (selects the mask variant of 0912 couplers; to be read when #7 supports couplers).
- `Union/Parameter@DefaultUnionParameter`: ETS writes the member in effect only and leaves the memory of a union without one at the static data (verified with the Tastsensor of `EHomeDemo.knxproj`, haumacher/ehome #6), so the default member is not needed for the download image.
- `ApplicationProgram@ProgramType`, `@IPConfig`, `@AdditionalAddressesCount` and the ETS bookkeeping of the program (`Hash`, `MinEtsVersion`, `PreEts4Style`, `ConvertedFromPreEts4Data`, `HelpFile`, …): not needed for the tables and steps of the samples; `IPConfig` and `AdditionalAddressesCount` belong to IP devices (gap 10).
- `Location@PtrResource` is read as the name of the resource (`ResourceLocation#pointerResource`), not as a reference; `ResourceType@Flavour` and `Feature@Name` are kept as the names KNX gives them.

Deliberately not read for parameter types:

- `UIHint` of `TypeNumber`, `TypeFloat` and `TypeTime` (slider, checkbox, time layouts): a hint for the ETS parameter editor, not a property of the value.
- `TypeFloat@DisplayFormat` is read only for its number of decimal places (`decimals`); its grouping and exponent are not modeled.
- `TypeDate@Encoding`: the only value is DPT 11, so it carries no information. Date and IP address values are kept as ETS writes them (`text`), they are not decoded into dates or addresses.
- `TypePicture` (a picture shown in the parameter dialog, no value): not supported; the import has no handler for it.

Value notation: ETS writes values in XML notation. A floating point value is read as an `xs:double` (a decimal point, optionally an exponent) and written back as a plain decimal with a point (`20.5`); the samples contain no floating point value, so this is an assumption taken from the XML schema (`Value` is a plain string there). A value that does not fit its type (not a number, outside the range, no entry of the enumeration) is kept unchanged as text, and the import logs a warning with its location.

Not needed for E-Home: `ProjectInformation` bookkeeping (numbers, dates, passwords, tracing), `HistoryEntries`, `ToDoItems`, `ProjectTraces`, `UserFiles`, `AddInData`, `SplitInfos`, `Baggages`, `PublicKeys`, `OrderNumberFormattingScript`, `InterfaceObject*`, `PropertyDataTypes`, `MediumTypes` (see above), and all `Hash`/`CheckSums`/`NonRegRelevantDataVersion`/`CompletionStatus` attributes.

## Round trip

The import is checked for completeness by its inverse: `test.de.haumacher.ehome.roundtrip.TestRoundTrip` imports each sample (`Test.knxproj`, `EHomeDemo.knxproj`, `KNX-Testsystem.knxproj`) into an empty database, exports it again (`de.haumacher.ehome.exporter.KnxprojExporter`, see [export.md](export.md)) and compares every XML file with the original element by element. The difference must be empty except for what [not-modeled.txt](not-modeled.txt) lists: that file is the machine-readable form of the "not modeled" items of this document (skipped files, elements and attributes, containers whose order the model does not keep, the master data reduced to what the project uses, schema defaults, the translatable texts compared per application language). An attribute or element that the import starts to read must leave that file, and one that a new sample brings and the import does not read makes the test fail until it is either imported or listed there.

The test then imports the export again: the second project has the same objects with the same external IDs, the shared data gains no object, and the download image of every device is the same.

## Open questions

- **Time zone of dates.** ETS writes dates without a time zone (`DeviceInstance@LastModified="2018-07-06T21:12:07"`, `LastDownload`). The import reads them as UTC (`DateValueProvider`), so `21:12` in the file shows as `23:12` in summer time in the app. Whether ETS means UTC or local time is not known yet; compare with the time ETS itself shows for a device of a real export, then adjust the format if needed.

- **Comments in RTF.** ETS stores comments as RTF documents, and the import skips them: `DeviceInstance@Comment` (gap 4), `GroupRange@Comment` and `GroupAddress@Comment` (gap 5), and likewise the comments of areas, lines, building parts and the project. Importing them needs an RTF conversion (e.g. to `tl.core:Html`) and an export of samples that actually contain comments.

## Limits of this analysis

- The table matches import handlers by parent and element name, because the mapping reuses handlers at several depths. Where a reused handler applies, an element can appear as handled under a parent that is not (for example `UnassignedDevices/DeviceInstance/ComObjectInstanceRefs`, while `UnassignedDevices` itself is not imported).
- It is based on schema 11 only. Current ETS versions write newer schema versions; the import does not check the namespace, so changed names would be skipped silently. A fixture from a current ETS is needed to check them.
