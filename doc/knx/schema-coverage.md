# KNX project schema: what the model covers

Comparison of the KNX project schema version 11 (`http://knx.org/xml/project/11`, ETS 4; the version of the fixtures in `ehome/samples/`) with the E-Home model and the ETS import (`etsImporter.xml`). What the import reads of schema 23 (ETS 6) is listed in "Project schema 23" below. The element-by-element table is in [schema-11-coverage.md](schema-11-coverage.md), generated by [schema-coverage.py](schema-coverage.py):

```
python3 doc/knx/schema-coverage.py KNXSchema.xsd ehome/src/main/java/de/haumacher/ehome/importer/etsImporter.xml
```

The XSD itself is not public and not in the repository.

## Overall

- Of 408 element paths of the schema, 251 are handled by the import; of 1138 attribute slots, 705 are read. The content of the `Languages` sections is read by a handler of its own (`translations`) and shows as not handled in the table.
- The model has a counterpart for exactly what the import reads, and almost nothing more. So "covered by the model" and "read by the import" mean the same thing here.
- IDs: the import keeps the `Id` ETS wrote (`extId`). An object created in the app gets an ID of the same shape (`de.haumacher.ehome.knx.ExtIds`): the ID of the object it belongs to and a number from a sequence of that scope, above every number imported there; the parts of a project's installation (areas, lines, devices, group ranges and addresses, building parts) are numbered from `ExtIds.APP_ID_BASE` (1000000) upward instead, far above the numbers of ETS, so the ID tells whether E-Home created the object (haumacher/ehome #125; objects created before carry numbers below and count as objects of ETS); types, enumeration entries, communication objects and products are named by their name, value, object number and order number, as in ETS. Switches, cases and the channel independent part have no ID (`choose`, `when` and `ChannelIndependentBlock` have none in ETS).
- Files: a project file (`.knxproj`, imported in the projects view) and the product file of a manufacturer (`.knxprod`, imported in the catalog view, `ImportProductDataJob`) are read with the same mapping; a product file is a project file without the project part (`knx_master.xml` and the `M-xxxx/` folders). The import of a product file refuses a file holding a project (`P-xxxx`) or an encrypted entry, and a file without manufacturer data. What a project or product file holds that the catalog already has is reused by its ID; a known application program is skipped.
- Baggage (haumacher/ehome #154): the files a manufacturer ships with its data (pictures of the parameter dialog, archives of icons and help texts, documents, plug-in installers) are kept with the manufacturer, from a product file as from a project file: `M-xxxx/Baggages.xml` (`Baggage@Id`, `@Name`, `@TargetPath`, `FileInfo@TimeInfo`) and the files `M-xxxx/Baggages/<TargetPath>/<Name>` become `ehome.catalog:Baggage` objects (`Manufacturer#baggage`: ID, name, folder, time, size and the content as it is, whatever its kind; nothing is interpreted or run). Read in Java (`de.haumacher.ehome.importer.BaggageImport`), not by the mapping, because the index and the files are separate entries in any order. A program names the files of `Static/Extension/Baggage@RefId` (`Program#baggage`), a product those of `Product/Baggages/Baggage@RefId` (`Variant#baggage`, a driver installer). A file is reused by its ID: the same or an older `TimeInfo` leaves it, a newer one replaces its content (reported). A listed file the archive lacks, or one above the size limit (16 MB per file, `BaggageImport.DEFAULT_SIZE_LIMIT`), is kept without content and reported; a later import holding it completes it. A file in the folder that the index does not list is reported and not imported. A known program an earlier import left without its files gains them from the next import of its file. Not read: the `InstallOnImport` and `FileInfo@Version` attributes (ETS bookkeeping), and the plug-in attributes of `Extension` (`EtsUiPlugin`, `EtsDownloadPlugin`, `EtsDataHandler`, `RequiresExternalSoftware`, haumacher/ehome #159). Baggage is not written back by the `.knxproj` export (not decided).
- Many unread attributes are irrelevant for E-Home (ETS bookkeeping: `Hash`, `NonRegRelevantDataVersion`, `CompletionStatus`, `LastModified`, passwords, history, to-dos). The gaps below are those that matter for understanding or operating an installation.

## Updating a project from ETS

A plain import always creates a new project, also for a file of a project the installation already has. The command "Update from ETS" ("Aus ETS aktualisieren") of the projects overview instead brings an existing project up to date with a new export of the same project from ETS (haumacher/ehome #125, `de.haumacher.ehome.importer.ProjectUpdate`, job `UpdateFromEtsJob`, with the password dialog and progress of the import):

- The file is imported as always (shared data reused) into a project of its own, whose KNX part is merged into the project in place; that project is deleted again, all in one transaction. A file of another project ID is refused.
- ETS wins on what the file carries, E-Home keeps what it alone holds; the split is declared once in `de.haumacher.ehome.knx.ProjectParts` and shared with the project file (`.ehome`, see [export.md](export.md)): of the project its name, group address style and KNX part are ETS's; of the KNX part the settings of the group addresses (runtime flags, unit, history with its archives, the identifier of haumacher/ehome #130) and a device's download revision are E-Home's. The name and the description of a group address are ETS's, but an empty one in the file keeps the project's (`ProjectParts.isKeptWhenEmpty`, haumacher/ehome #130): names assigned in E-Home survive an export from ETS that still lacks them, a name the file has wins. Every rule, function, page, Zigbee device, controller and recording stays.
- Objects of the installation are matched by their ID wherever they are (a group address re-addressed or renamed, a device moved to another line keep their identity and everything referring to them); objects without an ID (parameter settings, communication objects, connections, module instances) by their natural key within their container. Objects of ETS the file no longer has are deleted, unless E-Home's part uses them (a rule or function on a group address, a Zigbee device in a room, a function of a device, a page element, an expression naming the address): then the whole update is refused, naming each object and its user. The operating history (recordings, deployments) does not count; a recorded telegram keeps its address.
- Objects E-Home created (IDs in the app's range) are never deleted. The file adopts one where it brings the same object at its place — a device by line, individual address and product (another product refuses the update), a group address by its address, a range by its addresses, a building part by name and type in the same parent, an area or line by its address —: the object keeps its identity and takes the ID of ETS. Otherwise it stays; one whose container the file removed refuses the update.
- Ordered lists keep the user's order (the building structure, haumacher/ehome #71); new parts follow at the end of their container in the order of the file.
- The report lists per kind what was added, changed and removed, which objects of E-Home were kept or adopted, or that the file brings no changes (then no object is written).

- `ApplicationProgram@ProgramType`, `@IPConfig`, `@AdditionalAddressesCount` and the ETS bookkeeping of the program (`Hash`, `MinEtsVersion`, `PreEts4Style`, `ConvertedFromPreEts4Data`, `HelpFile`, …): not needed for the tables and steps of the samples; `IPConfig` and `AdditionalAddressesCount` belong to IP devices (gap 10).
- `Location@PtrResource` is read as the name of the resource (`ResourceLocation#pointerResource`), not as a reference; `ResourceType@Flavour` and `Feature@Name` are kept as the names KNX gives them.

Deliberately not read for parameter types:

- `UIHint` of `TypeNumber`, `TypeFloat` and `TypeTime` (slider, checkbox, time layouts): a hint for the ETS parameter editor, not a property of the value.
- `TypeFloat@DisplayFormat` is read only for its number of decimal places (`decimals`); its grouping and exponent are not modeled.
- `TypeDate@Encoding`: the only value is DPT 11, so it carries no information. Date and IP address values are kept as ETS writes them (`text`), they are not decoded into dates or addresses.

Value notation: ETS writes values in XML notation. A floating point value is read as an `xs:double` (a decimal point, optionally an exponent) and written back as a plain decimal with a point (`20.5`); the samples contain no floating point value, so this is an assumption taken from the XML schema (`Value` is a plain string there). A value that does not fit its type (not a number, outside the range, no entry of the enumeration) is kept unchanged as text, and the import logs a warning with its location; not for a value of the application program (`Parameter@Value`, `ParameterRef@Value`) of a hidden parameter (the access of the `ParameterRef`, otherwise of the `Parameter`, is `None`), which nobody sees or edits and ETS downloads as it stands (haumacher/ehome #83). A value of the project (`ParameterInstanceRef@Value`) is always reported.

Not needed for E-Home: `ProjectInformation` bookkeeping (numbers, dates, passwords, tracing), `HistoryEntries`, `ToDoItems`, `ProjectTraces`, `UserFiles`, `AddInData`, `SplitInfos`, `PublicKeys`, `OrderNumberFormattingScript`, `InterfaceObject*`, `PropertyDataTypes`, `MediumTypes` (see above), and all `Hash`/`CheckSums`/`NonRegRelevantDataVersion`/`CompletionStatus` attributes.

## Project schema 23 (ETS 6)

The import reads ETS 6 project files (namespace `http://knx.org/xml/project/23`) next to ETS 4 ones; the version is taken from the namespace of the files (`Importer#getSchemaVersion`). Checked against the ETS 6 exports of the test system (`ehome/samples/KNX-Testsystem-ETS6.knxproj`, `ehome/samples/KNX-Testsystem-ETS6-protected.knxproj`, password `test1234`) with ETS 6's own download of its actuator (`ehome-virtual/src/test/fixtures/ets-traces/ets6-download-1.3.5.txt`, compared in `TestEts6Download` of the development tooling), a real ETS 6.3 project with ten programs (outside the repository), and the artificial fixture `ehome/src/test/fixtures/TestEts6.knxproj` (`make-fixtures.py`; tests in `test.de.haumacher.ehome.schema23`). The format of the project part (`0.xml`) was first taken from the open-source reader xknxproject and is confirmed by the test system's export.

|---|---|

## Round trip

The import is checked for completeness by its inverse: `test.de.haumacher.ehome.roundtrip.TestRoundTrip` imports each sample (`Test.knxproj`, `EHomeDemo.knxproj`, `KNX-Testsystem.knxproj`) into an empty database, exports it again (`de.haumacher.ehome.exporter.KnxprojExporter`, see [export.md](export.md)) and compares every XML file with the original element by element. The difference must be empty except for what [not-modeled.txt](not-modeled.txt) lists: that file is the machine-readable form of the "not modeled" items of this document (skipped files, elements and attributes, containers whose order the model does not keep, the master data reduced to what the project uses, schema defaults, the translatable texts compared per application language). An attribute or element that the import starts to read must leave that file, and one that a new sample brings and the import does not read makes the test fail until it is either imported or listed there.

The test then imports the export again: the second project has the same objects with the same external IDs, the shared data gains no object, and the download image of every device is the same.

## Open questions

- **Time zone of dates.** ETS writes dates without a time zone (`DeviceInstance@LastModified="2018-07-06T21:12:07"`, `LastDownload`). The import reads them as UTC (`DateValueProvider`), so `21:12` in the file shows as `23:12` in summer time in the app. Whether ETS means UTC or local time is not known yet; compare with the time ETS itself shows for a device of a real export, then adjust the format if needed.

- **Comments in RTF.** ETS stores comments as RTF documents, and the import skips them: `DeviceInstance@Comment` (gap 4), `GroupRange@Comment` and `GroupAddress@Comment` (gap 5), and likewise the comments of areas, lines, building parts and the project. Importing them needs an RTF conversion (e.g. to `tl.core:Html`) and an export of samples that actually contain comments.

## Limits of this analysis

- The table matches import handlers by parent and element name, because the mapping reuses handlers at several depths. Where a reused handler applies, an element can appear as handled under a parent that is not (for example `UnassignedDevices/DeviceInstance/ComObjectInstanceRefs`, while `UnassignedDevices` itself is not imported).
- The table is based on schema 11. Schema 23 was compared with the import by the element and attribute paths of a real ETS 6 project (section "Project schema 23"); no XSD of schema 23 is available. The import still skips an element it has no handler for without a message (the default of the TopLogic XML import), so a construct of a newer schema that is missing from that section would be lost silently.
